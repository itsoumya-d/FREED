# Protection coverage and device validation

Audit date: 2026-10-02. The initial audit below describes the source snapshot in `docs/validation/artifacts/2026-10-02-protection-coverage/source-manifest.json`, not a shipped binary. The workspace is modified; Git HEAD alone does not identify the code tested. The manifest records SHA-256 hashes for 53 relevant files. The initial audit edited documentation and audit fixtures only. A subsequently authorized implementation repaired the bounded issues; see `docs/validation/artifacts/2026-10-02-protection-coverage/FIX_RECEIPT.md` and its separate source manifest for the current state. Neither phase operated browsers, simulators, phones, credentials, or public services.

FREED has useful protection layers, but cannot truthfully promise that it blocks every adult image, video, app, website, or bypass on every mobile device. Domain filtering cannot distinguish adult media from ordinary media delivered through the same encrypted service/domain. iOS does not expose other native apps' screens to this app; Android accessibility sees only exposed, supported fields and surfaces. Tests that classify a URL do not prove that a browser request was intercepted.

## Bounded corrections supported by evidence

1. **Paused filtering must not report fully active protection.** `src/lib/protection-readiness.ts:36` and Android native activation diagnostics `FreedProtectionModule.kt:1069` ignore `dnsGuardCaptivePaused`; `dnsGuardRuntimeReady` at `FreedVpnService.kt:1097` is a lifecycle check only. Keep “service running” separate from “adult filtering active”; require not paused for adult-filter activation and surface an explicit diagnostic code. Add a regression with a running/authorized guard plus `dnsGuardCaptivePaused=true`, and a resume case. Existing failing fixture is the exact evidence, not a physical sign-in test.

2. **Re-evaluate the Safari route at deferred render time.** `ios/FREEDSafariFocusShield/content.js:107` captures the old `surface` in DOMContentLoaded. A `/shorts` → `/watch` navigation before the callback renders a stale shield. The fixture reproduces this with the real shipped script. Resolve the current route in the callback, retain ordinary-route allowance, and test pre-ready navigation both directions, Back, and repeated callbacks. Real Safari execution remains a separate check.

3. **Disable unsupported Android lockdown setup.** Add the official always-on opt-out metadata for the DNS-only service, validate the merged manifest, and explain existing conflicting VPN/lockdown recovery. This is a compatibility correction; changing to a complete traffic VPN is a separate product/network architecture decision. [Android opt-out guidance](https://developer.android.com/develop/connectivity/vpn#opt-out-of-always-on).

4. **Qualify Private DNS privacy and coverage.** `VpnService.kt:627` always sends protected plaintext UDP/53; it does not branch on strict mode. `FreedProtectionModule.kt:1637` reads global setting strings rather than effective public LinkProperties. Public APIs expose active/private resolver state; Android instructs apps doing their own DNS lookups to honor encryption/strict resolver requirements. Add effective-state diagnostics and truthful unsupported/unverified status before claiming strict Private DNS support. Encrypted transport would require its own reviewed implementation. [Android LinkProperties requirements](https://developer.android.com/reference/android/net/LinkProperties#getPrivateDnsServerName()).

5. **Keep privacy statements precise.** Normal Android recovery interception does not use overlays, screenshot capture, or OCR. User-initiated custom calibration does create a temporary accessibility overlay (`FreedFocusShieldCalibration.kt:356`, `:445`); a blanket “FREED never uses overlays” statement is contradicted by source. iOS Safari uses a DOM pause layer, not a system screenshot/other-app overlay. Challenge photo verification is separately user-selected camera input. Keep these distinctions and do not introduce screenshot/OCR loops or screen-text storage.

## Optional iOS DNS settings direction — unimplemented

`NEDNSSettingsManager` can configure a system default DoH/DoT resolver without implementing a packet tunnel or DNS proxy extension. The installed iPhoneOS 26.5 SDK header confirms availability beginning with iOS 14.0; its hash/excerpts are in `ios-dns-settings-sdk-evidence.txt`. The required Network Extensions entitlement value is `dns-settings`, configured for the app and its signing profile. It is absent from current FREED entitlements; no distribution profile/capability was verified here. [Apple capability setup](https://developer.apple.com/documentation/xcode/configuring-network-extensions/), [Network Extensions entitlement](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.developer.networking.networkextension?changes=_5).

This API configures a resolver service, not the existing local reviewed-domain list. A domain-filtering DNS service would need to be selected or operated, with user consent, availability/captive-network handling, provider logging/retention disclosure, and revised privacy/store-review material. The user enables the saved configuration in Settings. A VPN's DNS can take precedence, and apps using their own encrypted resolution/cached addresses can evade a system default. It still cannot classify adult media inside encrypted mixed-domain native apps. [Apple manager API](https://developer.apple.com/documentation/networkextension/nednssettingsmanager?language=objc), [Apple encrypted DNS behavior](https://developer.apple.com/videos/play/wwdc2020/10047/?time=695).

No new resolver, entitlement, provider, packet tunnel, MDM profile, or public service was implemented. Evaluate this only as a separate consented capability extension.
