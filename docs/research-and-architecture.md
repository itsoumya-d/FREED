# FREED Research And Architecture

FREED is a recovery product first and a blocker second. The product goal is to keep normal browsing invisible and fast, then become very present during adult-content risk moments.

## Product Architecture

1. Onboarding
   - Identify user motivation, risky moments, and preferred reset style.
   - Avoid shame-heavy language.
   - End with a clear free-vs-premium choice.

2. Home
   - Streak and current clean time are the emotional anchor.
   - Daily pledge, breathing, reset, and journaling are first-class actions.
   - Protection status explicitly reassures users that normal browsing is allowed.

3. Shield
   - Adult-only classifier.
   - Default allow when confidence is not high enough.
   - Adult domains, adult search intent, and high-confidence explicit host tokens block.
   - Recovery, health, blocker, and education queries that mention adult terms are allowed when they do not contain consumption wording.
   - Hostnames with adult-looking tokens are allowed when the surrounding hostname clearly indicates recovery, health, research, support, or filtering context, while consumption-context hostnames still block.
   - Google, YouTube, Instagram, X/Twitter, education, gaming, streaming, productivity, and daily browsing domains are explicit allowlist entries.

4. Relapse Interruption
   - Detect adult-content intent.
   - Redirect to FREED.
   - Show streak risk, classifier reason, and supportive copy.
   - Free users see rewarded reset, then challenge.
   - Premium users go straight to challenge.
   - Self-triggered Panic Button/urge mode records a privacy-safe `self-urge.freed.local` intervention and skips rewarded ads for all users, because asking for help should never be delayed by monetization.
   - If a user reports an actual slip, the private reset log preserves the previous streak, optional trigger, and reflection while restarting the active streak without shame copy.

5. Challenge Engine
   - Scores interventions by time of day, attempt frequency, mood, streak age, premium status, private slip count/window/trigger summaries, coarse Android app/short-form session-duration buckets, aggregate recent failed-reset counts, and recent outcome feedback.
   - Uses onboarding reset preferences to lift matching categories such as physical, breathing, reflection, connection, or environment reset.
   - The local template engine keeps the simple UI categories but now also tags every generated template with production families: physical, outdoors, mindfulness, productivity, social, emergency, anti-relapse, late-night, and quick-reset. Premium custom resets and the legacy fallback pool infer those same families from category, title, why text, intensity, duration, and steps. Strict mode, sleep mode, outdoor preference, social preference, deep focus, weather context, and local urge-risk forecast use those families during local scoring before any remote AI call.
   - Can call a configured remote challenge-generation endpoint through `src/lib/challenge-generator.ts`; the endpoint must be production-safe, the request and JSON read are hard-timeout bounded through `src/lib/remote-provider-timeout.ts`, generated challenges receive only aggregate recovery signals, coarse slip-trigger categories, and no raw slip notes/triggers, are normalized, have link/domain echoes stripped from visible fields and generated IDs, are filtered for premium/free eligibility, and fall back to the local deterministic set if missing, invalid, stalled, or failed.
   - `app/api/challenges+api.ts` provides the server route scaffold for EAS-hosted generation. It keeps `OPENAI_API_KEY`/`GEMINI_API_KEY` server-only through `src/lib/server-ai-provider.ts`, bounds provider calls with `FREED_AI_PROVIDER_TIMEOUT_MS` and `FREED_AI_PROVIDER_RESPONSE_MAX_BYTES`, requests structured challenge JSON when configured, sanitizes generated output before display/storage, and returns local fallback challenges if the backend is missing or fails.
   - UI challenge categories: physical, breathing, reflection, connection, reset.
   - Completion updates recovery score, karma, and whether the intervention helped or the user still needs support.

6. CLARA
   - Supportive, concise recovery companion.
   - Uses local pattern-aware replies by default.
   - Can call a configured remote coach endpoint through `src/lib/ai-coach.ts`; the endpoint must be production-safe, the request and JSON read are hard-timeout bounded through `src/lib/remote-provider-timeout.ts`, user text is URL/domain redacted, risk context is reduced to host-level summaries, private slip context is reduced to count/window/coarse trigger-category summaries, remote output is redacted before display, and stalled/failed/missing remote service falls back to local support.
   - `app/api/clara+api.ts` provides the server route scaffold for EAS-hosted CLARA replies. It keeps `OPENAI_API_KEY`/`GEMINI_API_KEY` server-only, prefers OpenAI when configured, preserves Gemini as a fallback provider, bounds provider calls with `FREED_AI_PROVIDER_TIMEOUT_MS` and `FREED_AI_PROVIDER_RESPONSE_MAX_BYTES`, sanitizes remote model text, and returns local fallback support if the backend is missing or fails.
   - Crisis/self-harm language is handled locally with immediate safety resources and is not routed through the remote coach provider.
   - Production AI should use a server endpoint so model/API secrets stay off device and raw browsing history is never uploaded.
   - Production endpoint safety rejects insecure, local, private-network, reserved documentation, placeholder hosts, URL credentials, query strings, and fragments before release or backend smoke checks can pass.

## iOS Blocking Plan

Preferred:
- FamilyControls authorization.
- ManagedSettingsStore with `WebContentSettings.FilterPolicy.auto(...)` for adult filtering and exception handling.
- Shield extensions for blocked web domains and app/category shields.
- DeviceActivity for schedules and risk-window monitoring.
- Safari Content Blocker extension backed by the same adult-domain feed used by DNS/category rules. This gives Safari a low-latency first line of defense without screenshot analysis or packet inspection.
- iOS DNS filtering is unavailable in FREED. The client exposes no NetworkExtension DNS Settings path, full-tunnel VPN, or HTTPS interception layer.

Current implementation:
- `FreedProtectionModule.swift` requests FamilyControls authorization, exposes status, tracks whether the adult-content web filter is active, and applies or pauses a ManagedSettings adult-content web filter from the app bridge.
- The iOS settings handoff opens the app Settings page when UIKit is available and keeps the returned `active` status tied to the actual filter-active flag, not authorization alone.
- The native bridge can present Apple's `FamilyActivityPicker`, persist the selected app/category/domain token payload in a shared app group without immediately shielding the selection, apply selected shields only during active Night Guard windows or after the selected-target daily limit is reached, and report selection counts plus the device-local threshold reached date/status back to the Profile Native Protection card. During a Screen Time shield-sourced earned unlock it also reports the selected Screen Time token count, whether selected shields are paused, and whether adult web filtering is still active so physical-device evidence can prove the unlock did not disable adult-content protection; source-less or browser/adult-domain challenge windows do not pause selected Screen Time shields.
- The bridge exposes `startRiskWindowMonitoring` and `stopRiskWindowMonitoring` for a daily Night Guard DeviceActivity schedule with hour/minute precision. Scheduled state is returned separately from currently active filtering because the monitor extension applies the filter only during interval callbacks, and the React app syncs enabled sleep mode into this schedule.
- The iOS bridge also implements `configureBlockedAppPackages` as a Screen Time-compatible selected-target daily limit monitor: Android package IDs are ignored on iOS, the saved `FamilyActivitySelection` tokens are monitored through `DeviceActivityEvent` threshold events, and the monitor extension shields selected apps/categories/domains after the configured daily limit without reading app screens or scroll content. Native status exposes the `freed.selectedAppDailyLimitReached` device-local date so QA can distinguish a scheduled monitor from a fired threshold.
- The Profile Native Protection card exposes Apply/Pause Filter, Night Guard schedule controls, Choose Apps/Edit Selection, adult-domain feed fallback/success notices, and Safari rule sync metadata on iOS-capable builds, and avoids showing device-only controls in web preview.
- The onboarding flow now places explicit app-shield selection before the paywall and before permission setup. Android stores one supported primary package per user-facing app choice, expands known regional package aliases such as TikTok variants only for native app-timer sync, native pending handoffs normalize source packages, and the shared JS handoff converter only carries allowlisted app packages into earned-unlock source metadata. iOS defers actual app/category/domain picking to Apple's Screen Time picker during setup.
- The post-paywall protection setup screen now uses the shared permission plan to explain each platform permission separately, including why it is needed and what data boundary applies. It also includes a Test Protection step that retries native adult-domain feed sync, records adult-domain block, normal-site allow, and freshly refreshed native permission/feed readiness at the moment the user runs the test, without writing a blocked attempt into recovery history. The setup CTA only becomes Activation Complete after that test passes while current native readiness is still true, and iOS/Android builds do not enter the main app from setup until that activation path passes; web preview can continue as a preview only. On Android, activation requires a non-empty native adult-domain feed so DNS Guard and Accessibility classify against the embedded or reviewed synced feed rather than an empty list. Challenge verification permissions remain on-demand only.
- `FREEDShieldConfiguration` returns FREED-branded, non-shaming shield copy for selected app, category, and web-domain interruptions instead of framing every iOS shield as adult-site detection.
- `FREEDShieldAction` handles shield primary/secondary buttons without ads or punitive copy. Primary "Start recovery" writes a privacy-safe pending intervention into the shared app group, and the iOS bridge normalizes any stored handoff values back to host-only URLs before the app consumes them into the normal relapse interruption flow.
- `FREEDDeviceActivityMonitor` reconciles the adult-content web filter separately from selected app shields, preserves the web filter across Night Guard interval changes when the core adult filter remains active, loads the shared `FamilyActivitySelection`, applies selected app/category/domain shields during scheduled risk windows, and also applies them when the selected-target daily DeviceActivity threshold is reached. Only earned unlock windows carrying FREED's canonical Screen Time shield source marker pause selected shields; expired, source-less, tampered, or browser/adult-domain sourced windows are cleared or rejected while adult web filtering stays active.
- `FREEDSafariContentBlocker` serves `safari-content-blocker-rules.json` from the shared app group only after validating that the shared file is a non-empty block-only content-blocker rule list, falls back to the bundled `blockerList.json` when the shared file is missing or invalid, and is reloaded by `FreedProtection.configureSafariContentBlockerRules` after the active adult-domain feed is compiled and validated. Because the current Content Blocker target is block-only, the React app also accepts a privacy-safe `freed://intervention?source=ios-safari-short-form&rule=...` handoff for future Safari Web Extension or approved web-short-form challenge redirects. The production app registers the `freed` URL scheme in Expo config, the iOS app `Info.plist`, and the Android app manifest; the handoff still stores only the platform host, keeps browser challenge windows local, and cannot pause iOS Screen Time shields.
- The shared client bridge does not expose iOS DNS Settings methods or status. `dnsFiltering` remains a cross-platform capability because Android DNS Guard uses it; iOS reports it unavailable and release audits do not require a NetworkExtension entitlement or profile.
- `scripts/add-ios-screen-time-extensions.rb` idempotently creates the Screen Time and Safari content-blocker extension targets, adds framework/resource links, app target dependencies, Embed App Extensions wiring, keeps Family Controls plus app-group entitlements on Screen Time targets, and keeps the Safari extension limited to the shared app group entitlement.

## Android Blocking Plan

Preferred:
- Accessibility service limited to supported browsers and focused WebView URL/search text fields.
- Safe-search enforcement for supported search engines.
- Native no-history Activity handoff for immediate relapse interruption, avoiding `SYSTEM_ALERT_WINDOW` by default.
- Private DNS guidance for DNS filtering when the user wants network-level support.

Current prototype implementation:
- `FreedAccessibilityService` extracts known URL/search field resource IDs for stable and beta/dev/canary Chrome/Edge, Firefox variants, Brave, Opera, stable/beta Samsung Internet, DuckDuckGo, Vivaldi, and Kiwi, with a conservative field-gated text fallback.
- The fallback only considers focused, accessibility-focused, or editable URL/address/search-like controls in supported browser or WebView contexts, including raw address/search text before navigation, and ignores long/freeform page text so recovery articles, page bodies, or arbitrary form fields that merely mention adult domains do not trigger a handoff.
- `FreedUrlClassifier` mirrors the app-side adult-only classifier: explicit normal-domain allowlist first, adult search intent on safe sites, adult seed domains/tokens, default allow for unknown non-adult domains. Android Accessibility also classifies raw focused browser search text, blocks high-confidence adult intent through a redacted `focused-search.app.freed.local` handoff, and allows recovery/health/education phrasing without persisting the query.
- `src/lib/adult-domain-feed-sync.ts` resolves a remote public feed from `EXPO_PUBLIC_ADULT_DOMAIN_FEED_ENDPOINT` when configured, sends conditional checksum headers only after required native and Safari content-blocker layers report matching populated checksums, bounds device requests, validates feed freshness/readiness, and falls back to the embedded feed on failure. Android persists the normalized feed for Accessibility and DNS Guard; iOS syncs the reviewed adult-domain Content Blocker only and has no DNS Settings side path.
- Blocked browser attempts are stored as a pending intervention in Android shared preferences, the no-overlay native handoff posts a high-priority recovery notification before attempting the Activity launch, and `src/features/freed-app.tsx` consumes that pending intervention into the standard recovery flow on launch or foreground resume. Android and iOS native bridge reads reject and clear missing, future-dated, or older-than-ten-minute pending records before JS can open recovery UI, normalize legacy pending values to host-only redacted URLs, sanitize Android source-package values, and the React layer repeats the same freshness guard on launch/foreground resume.
- The service also supports opt-in package-level app shields for configured doomscroll apps. `FreedDoomscrollApps.kt` centralizes native Android package IDs, regional TikTok aliases, short-form rule IDs, and app-local handoff hosts so `FreedAccessibilityService` and `FreedProtectionModule` cannot drift separately. `FreedProtectionModule.configureBlockedAppPackages` now rejects arbitrary package names and persists only the supported YouTube, Instagram, TikTok, X/Twitter, and Reddit package IDs plus the configured daily app budget and short-form threshold. The React state stores one primary package per user-facing app choice, then `getActiveBlockedAppPackages` expands known native aliases such as TikTok's `com.zhiliaoapp.musically`, `com.ss.android.ugc.trill`, and `com.tiktok` before sync so regional installs are covered without cluttering the UI. `FreedProtectionModule.openUsageAccessSettings` opens Android Usage Access, `getStatus()` reports `usageStatsAuthorized`, and native status exposes aggregate same-day selected-app foreground minutes for QA. `FreedAccessibilityService` maintains an event-driven same-day foreground usage ledger for those packages, cross-checks user-enabled `UsageStatsManager` totals so app limits survive service restarts, interrupts only after the daily limit is reached while no earned unlock is active, schedules a source-aware relock when an earned unlock expires while the protected app remains foreground, and waits for sustained short-form consumption before triggering a `short-form:*` handoff while the app remains below its broader daily app limit. Current Android short-form rules cover YouTube Shorts (`short-form:youtube-shorts`), Instagram Reels (`short-form:instagram-reels`), and TikTok For You (`short-form:tiktok-feed`) using selected/focused Shorts, Reels, or For You surface evidence before scroll cadence can count and requiring that current selected short-form surface again when the threshold timer fires. Pending app handoffs use `configured-app:<package>` or a short-form rule plus an app-local host so analytics can count app interruptions without collecting browsing details.
- `FreedInterventionActivity` gives users an instant calm interruption screen while React Native warms, then opens the standard FREED recovery flow. Accessibility browser/WebView, app-limit, and short-form handoffs now carry the matched rule through the Activity and post the same visible no-overlay notification fallback before launch, so Android background-start restrictions still leave a challenge path. ## Data Model

Core tables/collections:
- `user_profile`: name, plan, onboarding answers, accountability settings, privacy preferences.
- `streak_state`: current streak, personal best, start date, relapse records.
- `block_attempts`: timestamp, source (`browser`, `search`, `manual-check`, `panic-button`, or opt-in Android `app`), host hash, category, confidence, intervention result.
- `challenge_events`: challenge id, category, started, completed, rating, duration.
- `discipline_settings`: daily limits, short-form interruption threshold, unlock duration, opt-in Android app shield package IDs, challenge intensity, outdoor/exercise/social preferences, strict/sleep/focus/work/weekend modes.
- `earned_unlocks`: verified-completion challenge windows with start, expiry, duration, source challenge, and redacted source host when available; only source-qualified native windows are mirrored to native protection so iOS Screen Time shields or Android package shields can pause and restore from their risk-window/daily-limit state without disabling adult web protection. Browser/adult-domain and panic completions remain local challenge windows. Challenge outcome feedback stays in `challenge_history` so "helped" can personalize future resets and "still-urging" can route the user to support without withholding the bounded relockable window that was earned by verification.
- `daily_checkins`: mood, urge level, sleep, notes.
- `coach_sessions`: local summary, user-approved exports only.
- `allowlist_rules`: normal domains, user exceptions, enterprise or partner rules.
- `blocklist_rules`: adult domains, high-confidence category domains, regional feeds.

Current prototype implementation:
- `src/lib/recovery-state.ts` defines the typed local recovery state and migration/hydration helpers.
- `src/lib/recovery-storage.ts` persists that state with Expo SQLite's localStorage polyfill.
- Persisted fields currently cover onboarding completion, quiz answers, verified premium entitlement status, verified premium plan metadata when the purchase/restore result identifies it, current/best streak, private slip records, protected attempts, completed challenge count, challenge history, challenge outcome feedback, discipline settings, earned unlock history, daily check-ins, mood/urge/sleep/reflection data, and last protected/opened timestamps.
- Active native-shield earned unlocks are pushed through the native `FreedProtection` bridge. JS recording and hydration cap earned windows at 120 minutes even if older or tampered local state contains a longer expiry. iOS stores a bounded expiry in shared app-group defaults only for Screen Time shield-sourced earned windows, clears selected app shields while that window is active, reapplies those shields after expiry only when a risk window is active or the selected-app daily limit has actually been reached, and preserves adult web filtering across Night Guard interval changes. Android JS and native code both resolve earned-unlock sources through the supported app package/short-form handoff allowlist before mirroring an unlock to native app shields. Android stores the bounded expiry plus inferred source package only when the unlock came from a configured app or short-form handoff, clears source-less or unsupported native unlock attempts, keeps adult-domain filtering active, scopes the unlock to that source package, and schedules a bounded relock deadline if the protected source app remains foreground after expiry. Browser/adult-domain and panic challenge completions stay as local challenge windows and do not pause native app shields.
- Challenge verification is on-demand and evidence-specific: motion challenges use accelerometer samples, walking/indoor movement uses pedometer or foreground location distance with multiple accurate foreground fixes to avoid GPS-drift unlocks, photo targets use fresh camera capture with on-device labels, calm resets use timers, and connection challenges require an explicit connection action without depending exclusively on a configured accountability partner.
- Android app shield selections are sanitized to the known doomscroll package list before storage, synchronized to the native Accessibility service with the user's daily app budget and short-form threshold, interrupted only after that budget is consumed or a sustained short-form threshold is met, and paused only for the package that earned the current unlock so users earn time without globally weakening other configured app shields.
- Protected attempts store host-level redacted URLs, host, rule, source, verdict, and timestamp. iOS Screen Time shield handoffs are normalized as opaque app-shield interventions with unknown category rather than browser/adult events. Raw path/query URLs are not persisted by the JS recovery state, and hydration redacts legacy raw attempt URLs.
- Android Accessibility and iOS Shield pending interventions pass host-level redacted URLs into the app instead of exposing raw browser candidate strings, paths, queries, ports, credentials, or arbitrary package strings.
- Weekly recovery reports are generated locally from the last seven days of redacted protected attempts, private slip records, completed challenges, and daily check-ins. Reports include risk count, slip count, reset count, check-in count, learned risk window, slip window, slip trigger, best-performing reset, risk momentum, strongest pattern, next focus, and wins.
- Recovery XP, levels, and achievement badges are derived locally from streaks, best streak, completed/helpful challenges, check-ins, protected attempts, and honest reset logs. They are not stored as separate mutable state.
- Accountability partner settings are local and opt-in: enabled flag, partner name, SMS/email method, contact value, message template, and last-contact timestamp.
- Attempt counts are day-scoped in local time so analytics do not treat lifetime protected attempts as today's risk load.
- Optional-at-runtime remote analytics now has a concrete production path: release preflight requires a production-safe HTTPS `/api/analytics` aggregate ingestion endpoint, the Analytics screen persists explicit current-version `RecoveryState.analyticsSharing` consent through `updateAnalyticsSharingSettings`, and `sendGatedAnalyticsPayload` refuses to send until explicit current-version consent, a current configured endpoint match, aggregate-only controls, and short retention are configured; the client request is bounded by `EXPO_PUBLIC_ANALYTICS_TIMEOUT_MS` and the client JSON read is bounded by `EXPO_PUBLIC_ANALYTICS_RESPONSE_MAX_BYTES`, `app/api/analytics+api.ts` rate-limits requests through the shared hashed backend limiter and rejects stale consent versions plus raw attempts, URLs/domains, notes, contacts, transcripts, receipts, and support templates; the `aggregate-v5` snapshot includes hydrated active app opens, AppState-derived foreground minutes, compact blocked-attempt source breakdowns, full hourly risk buckets, weekly unlock frequency, seven-day streak history, relapse reset rates, days since last reset, and category-level challenge success; and server-side Supabase insertion uses `SUPABASE_SERVICE_ROLE_KEY` only on the backend, with `FREED_ANALYTICS_SUPABASE_TIMEOUT_MS` preventing stalled inserts while Supabase derives analytics expiry from `received_at + data_retention_days`.

Privacy:
