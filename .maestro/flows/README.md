# Native feature flows

These flows run against an installed FREED binary through native accessibility. They are UI smoke tests; the manifest has additional scenario, physical-device, live-service and motion obligations. A successful flow never marks an entire feature verified.

Use `node scripts/run-feature-verification.js --mode ios|android --run-ui --device <disposable-id> --isolation <fixture.json>`. The runner rejects the owner's existing iPhone simulator and requires a bound disposable fixture. Flows never erase app data or the iOS Keychain. Every flow can change navigation; flows tagged `local-write` also modify only the disposable test history.

Flows tagged `external-service` require an app build pointed at isolated emulators or sandbox services. Never run them against the owner's account, mailbox, store account, backend or support contacts. Actual signup/reset delivery, store checkout, messages and deletion need their dedicated scenario receipts. Generic flows only open compose or confirmation views; they never send messages or complete purchases.

Selectors use native `testID` values and current visible accessibility labels. `screen-<route>` markers are non-grouping route containers. Reading labels and awaiting rendering is appropriate smoke evidence; source text or an animation recording does not establish runtime behavior or frame timing.

Flows with English text selectors require an English fixture. Language, appearance, and draft flows use stable IDs where available; an English smoke run does not cover the ten-language review matrix. Korean replaces Bengali in the language smoke flow.

First launch requires a genuine account before private Today. On an English signed-out disposable fixture, Welcome's Get started opens the five-question quiz; each answer is retained when moving back through questions. The summary shows the chosen answers, and Continue to account opens required account options. Back to Welcome cancels that account presentation without granting private access. I have an account enters account options directly. A fresh account deep link can be guarded to Welcome, and a summary with missing answers returns to the quiz; neither shortcut establishes the real journey prerequisites.

`onboarding-welcome` checks the first quiz controls and return to Welcome. `onboarding-plan` starts at Welcome and reuses the unchanged `onboarding-quiz.yaml` to supply all five answers before asserting the summary and account gate. `account-options` uses the Welcome account control, checks Google/Apple/email choices, opens create/sign-in email modes without submitting credentials, and cancels through the explicit Back to account options and Back to Welcome controls. These entry flows assert that private Today and Skip for now are unavailable. They do not tap providers or send signup, sign-in, verification, or password-reset requests. Profile provider linking has a separate real-owner context and Cancel label; these signed-out entry flows do not verify it.

The provider checks target native iOS/Android. Google remains visible on native even when configuration disables it, so visibility does not prove provider readiness. Apple is always offered on Android; iOS requires the device's Apple authentication capability. The plan/account flows require an Apple-capable iOS fixture (including Root's iOS 26.5 F5 probe) or Android and deliberately fail if the expected Apple control is absent. This is a documented device prerequisite, not a new runner fixture field or an optional visibility branch. Record an unsupported device/capability or inaccessible selector as a gap; do not call a missing provider a pass. The native account screen is an app-owned modal, so these flows await its accessibility labels instead of relying on the underlying `screen-account` route marker.

Help/SOS remains available from Welcome and required account options before sign-in. It opens free, ad-free Basic Help; closing returns to the originating entry screen without private access. Its breathing, interruption, and return behavior needs separate native evidence, beyond these three entry flows.

Private flows require a separately prepared disposable fixture with a real current signed-in test user, any required introduction progress and owner-scoped offer decision, plus the flow's stated data/device prerequisites. Entry-flow success does not prepare or verify that fixture, confer premium membership, activate protection, or satisfy private-feature scenarios. Keep signed-out entry runs and signed-in private runs separately bound to their fixture and installed binary; never manufacture account or entitlement authority or reset app data/Keychain to pass a flow.
